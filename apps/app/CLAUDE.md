# apps/app

## Purpose
Vite + React 19 SPA. The set is the member app, and a registered set is a venue screen (`docs/adr/0016`): boot mark, then a session check, then the three channel tiles or the login form on the same set. Dashboard (Overview, Campaigns, Wallet, Settings, admin Moderation) is a page of its own at `/dashboard`, opened from the set in a new tab. Runs on port 3000 and calls the API origin configured by `VITE_API_URL`. `VITE_EMBED_URL` still points at the unmaintained web embed bundle the API serves; no dashboard page reads it.

## Pages
- `routes/capychannel/home.tsx` the set — `/` is the product. Every launch plays the boot mark first. Then a session sees the channel tiles (Images/Video, Wallpaper, Capy Channel). No session sees the login form on the set; the app never sends a visitor to the landing site on its own. `?auth=` picks the form (`login`, `signup`, `forgot`), and `/login`, `/signup` and `/forgot-password` redirect here with that parameter. A `?redirect=` path (same origin only, `src/lib/redirect.ts`) is where the set goes once the visitor signs in. The landing page checks the session and sends a member to the app; the lockup links back to it with `?from=app` (`src/lib/landing.ts`), which skips that check. `pnpm launch:check` refuses an app and a landing site on one origin, and an API on another site than the app, because its session cookie would be third-party. The account menu opens the dashboard in its own named tab (`src/lib/dashboard-tab.ts`), so a second click brings that tab forward, or logs out. The open bands on the ad ticker open the booking page in the same tab. The Images/Video tile opens the library (`components/capychannel/library.tsx`): the member adds files, selects one or many, deletes, and plays. The first Add asks for consent to upload (`upload-consent.tsx`); nothing is chosen before they agree. Files go up through the presign routes, and the list of public URLs lives in `localStorage` per member (`src/lib/library.ts`), because the API has no table for it yet. The Wallpaper tile opens the same frame (`components/capychannel/wallpapers.tsx`), with Play alone in the middle of the screen and no Upload or delete. One tile is one collection, and only one collection plays at a time: a click selects it, and Play plays it. A tile under the pointer loops through its photos. The collections come from the preset desk (`GET /presets`, `src/lib/presets.ts`, `presetCollections` in `channels/catalog.tsx`): each has a name (printed under the tile), an optional author, a link, and its photos, and one with no photo stays off the chooser. While the desk holds no collection with a photo, `WALLPAPER_COLLECTIONS` in `channels/catalog.tsx` stands in: the bundled demo, with a full file and a thumbnail per photo in `src/assets/wallpapers/<collection>/`. The set plays a collection's photos one at a time, ten seconds each (`channels/wallpaper.tsx`), with "Photo by" and the author (or the collection's name, when it has no author) in the lower right corner above the ad bar. A click anywhere on the photo opens the collection's link in a new tab. The Capy Channel tile plays at once, with no chooser (`channels/tv.tsx`): hand-picked YouTube videos played like live TV, in plain `youtube-nocookie` embeds. `channels/tv-guide.json` is the one file of videos, filled in by hand; `tv-guide.ts` checks it with zod, and a file that fails shows "No signal" instead of taking the set down. A `loop` channel needs each video's length, because an embed cannot say it; a `live` channel plays its first stream, and any stream after it is a spare. `tv-schedule.ts` holds the pure rules: every viewer reads the same clock, so every viewer on a channel sees the same video at the same second, and a channel opens mid-video. The set fills the window on a laptop, a monitor, an iPad and an iPhone, the way a YouTube page does. The video keeps 16:9 and is never cut: a window of another shape shows black bars beside or above it. The interface sizes come from the largest 16:9 box in the window (`--fh`, `--fw` in `capychannel.css`), with floors in px for a phone, and `useViewportFitCover` (`src/lib/viewport.ts`) lets the set run under an iPhone's notch while it is mounted. On a window held on its side the video is centred and the overlays lie over it. Held upright, the video goes to the top under the top bar, and the details, the channel buttons and Up next stack under it and do not fade. Scanlines lie over the video; the brand blue shows only under the snow while a video loads. The video takes no pointer and no focus, because a mouse that moves over a frame from another site never reaches the page, and the controls could not wake. The overlays are one group: when the mouse moves over the picture, the top bar (Back, the online count, the account), the video's details and the channel buttons in the lower left, and Up next in the lower right all show at once; after the idle time they all go at once, and a pointer resting on any of them holds them all. Up next is the next video's thumbnail (YouTube's own `mqdefault` still, no key), title, creator and start time. A live channel has no Up next. The channel buttons show no focus ring. The time line gives the video's start and end as clock times in the computer's time zone, or LIVE. Keys 1 to 9 tune, the up and down arrows step, and the last channel is kept in `localStorage`. A paused set (dashboard open, tab hidden) holds no player, so the sound stops; coming back tunes again from the clock. The ad ticker stays at the bottom, as on the other channels.
- `routes/dashboard/index.tsx` Overview — the balance card (total earning, available, cash out, with the notes behind info tooltips and the payout setup button), the running ads card, the payout history chart, and recent wallet activity
- `routes/dashboard/campaigns.tsx` — the slot page. The ticker loop holds `economy.slot.count` slots at one flat price for one term. The page shows the offer (price, term, slots left), the slot grid, and the member's slots under a state menu. Booking and editing are a page, not a dialog: `routes/dashboard/slot-book.tsx` serves `/dashboard/campaigns/book?slot=<position>` and `/dashboard/campaigns/:campaignId/edit`, and `components/campaigns/slot-form.tsx` holds the form with a true-size preview. Pure rules live in `src/lib/slots.ts`. The API holds the slot: `GET /slots` lists this member's bookings and `GET /slots/loop` prints the twenty positions. `POST /slots` books the campaign, its creative and the charge in one request. `SlotTicker` draws the loop flat with a label on each position (`#1` to `#20`); a press on an open band picks that position, and a held band is a paid booking that waits for review.
- `routes/dashboard/wallet.tsx` Wallet (`/dashboard/ledger` redirects to `/dashboard/wallet`) — filterable by reason, state and lot; cursor-paginated. The panel above it carries the cash-out dialog (identity on file, then the request), and the table under it lists every payout this member asked for
- `routes/dashboard/settings.tsx` — two-panel layout; sections live in `src/components/settings/`. Admin-only Moderation, Payouts, Complimentary slots (give a member a slot for nothing, `GET/POST /admin/slots/comped`), Top-ups (the refund desk), Feedback, Presets (the wallpaper collections: name, link, author, photos) and Releases sections appear there for `role === 'admin'`; `/dashboard/admin/*` redirects in
- `routes/dashboard/screens.tsx` Screens — the member's registered screens, with the photo and the review state; rename and archive. A screen is added from the set it runs on, so the page has no add control
- `/dashboard/products` redirects to Campaigns, `/dashboard/devices` redirects to Screens, and `/dashboard/placements` redirects to `/`, so links people saved before still work
- Query hooks live in `src/lib/{campaigns,slots-api,stats,ledger,admin,payouts,devices}.ts` on top of `src/lib/api.ts` (`apiFetch`). `campaigns.ts` owns listings too, because a listing only ever appears inside its campaign

## The set as a screen
A signed-in member with no device key sees "Earn from this screen" in the account menu (`components/capychannel/register-screen.tsx`): name, location, venue type, open hours, and a required photo through `/uploads/device-photo/presign`. The key `POST /devices` answers is the set's credential from then on. `src/lib/screen/use-screen.ts` holds the key, the ring batch and the report queue in `localStorage` (`capychannel.screen.*`): it asks `GET /ring` every minute while the screen waits for review, and only when fewer than `economy.ring.refillAtLaps` laps stay once it earns, because every call opens plays. The bar shows a chip for the review state. With an approved key the crawl draws the ring from `/ring`, and `ticker.tsx` watches every printed band with an `IntersectionObserver`; `src/lib/screen/crossings.ts` counts a crossing only when a band enters on the right, leaves on the left, the page stays visible, and it takes most of `CROSS_MS`. A registered set with no session plays its last channel (`saveScreenPick` in `resume.ts`, in `localStorage`) and the menu shows only "Sign in". One tab per browser reports, through a Web Lock; another tab shows the unpaid ring. Settings → Moderation lists the screens that wait for review, with the photo. The pure rules have Vitest tests (`pnpm --filter @repo/app test`).

## Conventions
- All env access through `src/lib/env.ts` (validated via `@t3-oss/env-core`) — never `import.meta.env.VITE_*` directly
- Authenticated API calls must include `credentials: 'include'` — session auth is cookie-based
- Auth state via `useSession()` from `src/lib/auth.ts` — never manage session state manually
- Dashboard pages must be nested inside the `/dashboard` route in `router.tsx` so `DashboardLayout` wraps them. It mounts only with a session; with none it redirects to `/?auth=login&redirect=<path>`. The dashboard is not under `MemberLayout`, so the set does not play behind it.

## Common tasks

### Add a new dashboard page
1. Create `src/routes/dashboard/<name>.tsx`
2. Add a `<Route>` inside the `/dashboard` parent in `router.tsx`
3. Add a title to `PAGE_TITLES` and a nav item to `navItems()` in `src/routes/dashboard/layout.tsx`

### Add a new API call
Use `useQuery` or `useMutation` from TanStack Query. Fetch against `${env.VITE_API_URL}/<endpoint>` and include `credentials: 'include'` when the endpoint depends on the user session.

### Enable Google sign-in
Add a button calling `signIn.social({ provider: 'google', callbackURL: '/dashboard' })`. No other config needed here — Google OAuth activates in `packages/auth` when the env vars are set.

### Browse the component library
Navigate to `http://localhost:3000/_dev/components` in dev mode. This route is tree-shaken from production builds.

### Change the Capy Channel's videos
Edit `src/components/capychannel/channels/tv-guide.json`. Each video needs its YouTube id, title and creator, and in a `loop` channel its length as `m:ss` or `h:mm:ss`. Use horizontal videos of 3 to 60 minutes, never a Short. Then open `http://localhost:3000/_dev/tv-embeds` in dev mode: it shows every video in the file as a small player, and lists anything wrong with the file. Take out a video that says "Video unavailable" or that blocks playback on other websites. Do this check each week, because a video can be deleted and a live stream can end and come back with a new id.

## Gotchas
- Dev server: port 3000; the API defaults to `http://localhost:3001`. A Vite `/api/*` proxy exists for relative requests, but the current clients use the absolute `VITE_API_URL`.
- Icons come from `@phosphor-icons/react`, not lucide. Phosphor takes `weight` (`bold`, `fill`, …) instead of `strokeWidth`
- The `/_dev/components` and `/_dev/tv-embeds` routes only exist in dev; they are absent from production builds
- `vercel.json` sends every path outside `/assets/` to `index.html`, because the router runs in the browser. Without it, a reload of `/dashboard` (or any deep link) gets a 404 from Vercel. `/assets/` stays out, so a stale hashed chunk 404s instead of returning HTML
- The Capy Channel cannot know when a browser blocks sound: a plain embed tells the page nothing. The press on the tile is the gesture that allows sound, which is enough in Chrome. Safari, and an iPad above all, can still refuse. The video takes no pointer, so the member cannot press play in the player either. The YouTube IFrame Player API is the fix when the demo grows
