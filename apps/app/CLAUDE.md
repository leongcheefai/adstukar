# apps/app

## Purpose
Vite + React 19 SPA. CapyTV is the member app: boot mark, then a session check, then the three channel tiles or the login form on the same set. Dashboard (Overview, Campaigns, Wallet, Settings, admin Moderation) opens as a Vaul drawer over CapyTV at `/dashboard`. Runs on port 3000 and calls the API origin configured by `VITE_API_URL`. `VITE_EMBED_URL` still points at the unmaintained web embed bundle the API serves; no dashboard page reads it.

## Pages
- `routes/capychannel/home.tsx` CapyTV — `/` is the product. Every launch plays the boot mark first. Then a session sees the channel tiles (Images/Video, Wallpaper, Capy Channel). No session goes to the landing site (`VITE_WEB_URL`), unless the URL carries `?auth=`, which shows the login form on the set. `src/lib/landing.ts` refuses a landing URL on the app's own origin (a loop) or on localhost from a non-local page (a production build without `VITE_WEB_URL`); then the form shows instead. `pnpm launch:check` refuses both setups, and an API on another site than the app, because its session cookie would be third-party. `/login`, `/signup` and `/forgot-password` redirect here with that parameter. The landing page does the reverse check and sends a session to the app. Account menu opens the dashboard as a Vaul drawer over CapyTV, or logs out. The Images/Video tile opens the library (`components/capychannel/library.tsx`): the member adds files, selects one or many, deletes, and plays. The first Add asks for consent to upload (`upload-consent.tsx`); nothing is chosen before they agree. Files go up through the presign routes, and the list of public URLs lives in `localStorage` per member (`src/lib/library.ts`), because the API has no table for it yet. The presets an admin set (`GET /presets`, `src/lib/presets.ts`) sit at the front of the row; they select and play like the member's own and carry no delete. The Wallpaper tile opens the same frame (`components/capychannel/wallpapers.tsx`), with Play alone in the middle of the screen and no Upload or delete. One tile is one collection, and only one collection plays at a time: a click selects it, and Play plays it. A tile under the pointer loops through its photos. `WALLPAPER_COLLECTIONS` in `channels/catalog.tsx` holds each collection's name (printed under the tile), its author, its link, and its photos; each photo has a title, a full file and a thumbnail in `src/assets/wallpapers/<collection>/`. The set plays a collection's photos one at a time, ten seconds each (`channels/wallpaper.tsx`), with the title and the author in the lower right corner above the ad bar. A click anywhere on the photo opens the collection's link in a new tab. The collection is demo content. The Capy Channel tile plays at once, with no chooser (`channels/tv.tsx`): hand-picked YouTube videos played like live TV, in plain `youtube-nocookie` embeds. `channels/tv-guide.json` is the one file of videos, filled in by hand; `tv-guide.ts` checks it with zod, and a file that fails shows "No signal" instead of taking the set down. A `loop` channel needs each video's length, because an embed cannot say it; a `live` channel plays its first stream, and any stream after it is a spare. `tv-schedule.ts` holds the pure rules: every viewer reads the same clock, so every viewer on a channel sees the same video at the same second, and a channel opens mid-video. The video fills the set, with scanlines over it; the brand blue shows only under the snow while a video loads. The video takes no pointer and no focus, because a mouse that moves over a frame from another site never reaches the page, and the controls could not wake. The overlays are one group: when the mouse moves over the picture, the top bar (Back, the online count, the account), the video's details and the channel buttons in the lower left, and Up next in the lower right all show at once; after the idle time they all go at once, and a pointer resting on any of them holds them all. Up next is the next video's thumbnail (YouTube's own `mqdefault` still, no key), title, creator and start time. A live channel has no Up next. The channel buttons show no focus ring. The time line gives the video's start and end as clock times in the computer's time zone, or LIVE. Keys 1 to 9 tune, the up and down arrows step, and the last channel is kept in `localStorage`. A paused set (dashboard open, tab hidden) holds no player, so the sound stops; coming back tunes again from the clock. The ad ticker stays at the bottom, as on the other channels.
- `routes/dashboard/index.tsx` Overview — the balance card (total earning, available, cash out, with the notes behind info tooltips and the payout setup button), the running ads card, the payout history chart, and recent wallet activity
- `routes/dashboard/campaigns.tsx` — the slot page. The ticker loop holds `economy.slot.count` slots at one flat price for one term. The page shows the offer (price, term, slots left), the slot grid, and the member's slots under a state menu. Booking and editing are a page, not a dialog: `routes/dashboard/slot-book.tsx` serves `/dashboard/campaigns/book?slot=<position>` and `/dashboard/campaigns/:campaignId/edit`, and `components/campaigns/slot-form.tsx` holds the form with a true-size preview. Pure rules live in `src/lib/slots.ts`. The API holds the slot: `GET /slots` lists this member's bookings and `GET /slots/loop` prints the twenty positions. `POST /slots` books the campaign, its creative and the charge in one request. `SlotTicker` draws the loop flat with a label on each position (`#1` to `#20`); a press on an open band picks that position, and a held band is a paid booking that waits for review.
- `routes/dashboard/wallet.tsx` Wallet (`/dashboard/ledger` redirects to `/dashboard/wallet`) — filterable by reason, state and lot; cursor-paginated. The panel above it carries the cash-out dialog (identity on file, then the request), and the table under it lists every payout this member asked for
- `routes/dashboard/settings.tsx` — two-panel layout; sections live in `src/components/settings/`. Admin-only Moderation, Payouts, Top-ups (the refund desk), Feedback, Presets (the photos and clips every library starts with) and Releases sections appear there for `role === 'admin'`; `/dashboard/admin/*` redirects in
- `/dashboard/products` redirects to Campaigns, `/dashboard/devices` redirects to Overview, and `/dashboard/placements` redirects to `/`, so links people saved before still work
- Query hooks live in `src/lib/{campaigns,slots-api,stats,ledger,admin,payouts}.ts` on top of `src/lib/api.ts` (`apiFetch`). `campaigns.ts` owns listings too, because a listing only ever appears inside its campaign

## No device UI
The dashboard has no device UI. A member does not register a screen, and Moderation reviews listings only. The pool card at the top of Moderation reads `GET /admin/pool`: the week's slot revenue beside the week's earn (docs/adr/0010). The API still has the device routes. The admin payout review still shows the screen signals that the API sends.

## Conventions
- All env access through `src/lib/env.ts` (validated via `@t3-oss/env-core`) — never `import.meta.env.VITE_*` directly
- Authenticated API calls must include `credentials: 'include'` — session auth is cookie-based
- Auth state via `useSession()` from `src/lib/auth.ts` — never manage session state manually
- Dashboard pages must be nested inside the `/dashboard` route in `router.tsx` so `MemberLayout` (CapyTV) and `DashboardLayout` (Vaul drawer) wrap them. The drawer only mounts when a session exists.

## Common tasks

### Add a new dashboard page
1. Create `src/routes/dashboard/<name>.tsx`
2. Add a `<Route>` inside the `/dashboard` parent in `router.tsx`
3. Add a title to `PAGE_TITLES` and a nav item to `navItems()` in `src/routes/dashboard/layout.tsx`

### Add a new API call
Use `useQuery` or `useMutation` from TanStack Query. Fetch against `${env.VITE_API_URL}/<endpoint>` and include `credentials: 'include'` when the endpoint depends on the user session.

### Enable Google sign-in
Add a button calling `signIn.social({ provider: 'google', callbackURL: '/dashboard' })`. No other config needed here — Google OAuth activates in `packages/auth` when the env vars are set.

### Browse the component library
Navigate to `http://localhost:3000/_dev/components` in dev mode. This route is tree-shaken from production builds.

### Change the Capy Channel's videos
Edit `src/components/capychannel/channels/tv-guide.json`. Each video needs its YouTube id, title and creator, and in a `loop` channel its length as `m:ss` or `h:mm:ss`. Use horizontal videos of 3 to 60 minutes, never a Short. Then open `http://localhost:3000/_dev/tv-embeds` in dev mode: it shows every video in the file as a small player, and lists anything wrong with the file. Take out a video that says "Video unavailable" or that blocks playback on other websites. Do this check each week, because a video can be deleted and a live stream can end and come back with a new id.

## Gotchas
- Dev server: port 3000; the API defaults to `http://localhost:3001`. A Vite `/api/*` proxy exists for relative requests, but the current clients use the absolute `VITE_API_URL`.
- Icons come from `@phosphor-icons/react`, not lucide. Phosphor takes `weight` (`bold`, `fill`, …) instead of `strokeWidth`
- The `/_dev/components` and `/_dev/tv-embeds` routes only exist in dev; they are absent from production builds
- The Capy Channel cannot know when a browser blocks sound: a plain embed tells the page nothing. The press on the tile is the gesture that allows sound, which is enough in Chrome. Safari, and an iPad above all, can still refuse. The video takes no pointer, so the member cannot press play in the player either. The YouTube IFrame Player API is the fix when the demo grows
